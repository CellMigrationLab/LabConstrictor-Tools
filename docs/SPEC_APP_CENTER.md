# Spec: App Center (how to find apps built with LabConstrictor)

Status: proposal, nothing built. For review before any work starts.

## Goal

A user can see every app built with LabConstrictor in one place, install it
for their system, and open its tools from Napari, Fiji or QuPath. A developer
gets listed by doing almost nothing.

## Principle

The apps already announce themselves. Detection is by **convention**, not by
registration: an app is listed if its repository carries two things, both
added by the template.

1. The GitHub topic `labconstrictor-app`.
2. A small file `labconstrictor-app.yaml` at the repository root.

No central database is edited by hand, so the list never goes stale because
someone forgot to submit a pull request.

## 1. The metadata file

Generated by the template next to `construct.yaml`; the developer fills in a few lines.

```yaml
# labconstrictor-app.yaml
name: GuessTheCondition
summary: Can you tell your conditions apart by eye? A timed guessing game with statistics.
authors: [Guillaume Jacquemet]
license: MIT
kind: game              # analysis | segmentation | simulation | game | training | utility
categories: [teaching, microscopy]
hosts: [napari, fiji, qupath, notebook]   # where its tools work
tools_module: guessthecondition_lc_tools  # omit if the app has no tools
doi: 10.5281/zenodo.0000000               # optional
homepage: https://github.com/CellMigrationLab/GuessTheCondition
```

Rules: at most 12 lines of required fields (`name`, `summary`, `kind`, `hosts`);
everything else optional. `labconstrictor_tools check` validates the file
(unknown keys and missing required fields are errors with a fix hint).

## 2. The catalog

A new repository `CellMigrationLab/LabConstrictor-Apps` containing:

- **A scheduled GitHub Action** (daily, and on demand). It searches GitHub for
  repositories with the topic `labconstrictor-app`, reads each
  `labconstrictor-app.yaml`, reads the latest release, and writes `apps.json`:
  metadata plus, per app, the version and the installer links per system
  (Windows, macOS Apple Silicon, Linux) taken from the release assets.
- **A static page** (GitHub Pages) that reads `apps.json`: a searchable grid
  (name, summary, kind, hosts, version, download buttons per system). No
  server, no database.
- **`verified.txt`**, an allowlist of repositories we have checked. The page
  shows a "verified" badge for those and a short note for the others
  ("community app, not reviewed"). Listing never implies verification.
- **A removal rule:** repositories without a release, with a malformed file, or
  archived are skipped, and the Action's log says why (the developer can read it).

`apps.json` is also published as a plain file, so any tool can consume it.

## 3. In the hosts

A **Browse apps** entry in each host reads `apps.json` (cached, works offline
from the last copy):

| Host | What the user sees |
|---|---|
| Napari | a list in the LabConstrictor dock: name, summary, version, "Open download page"; installed apps are marked |
| Fiji | a menu item that opens a dialog with the same list |
| QuPath | the same, in the LabConstrictor menu |

Installed apps are those found in the registry. When the catalog has a newer
version than the registered one, the host shows "update available" with the
download link. Hosts never install anything silently; they only open the
release page.

## 4. Safety and trust

- The catalog lists links, it does not host or run code.
- Verified badge only for allowlisted repositories.
- `apps.json` contains only the metadata fields above and links on
  `github.com`; the page escapes everything it shows.
- A takedown is one line removed from the topic or a PR deleting the repository
  from the catalog (a `blocked.txt` list).

## 5. Work packages (each a small PR)

1. Template: add `labconstrictor-app.yaml`, add the topic to the setup guide, `check` validation (Tools + template repo).
2. Catalog repository: Action, `apps.json` schema, static page, `verified.txt`, `blocked.txt`.
3. Napari **Browse apps**, then Fiji, then QuPath.
4. Back-fill: add the file and topic to NucleiSky, CellTracksColab, VLab4Mic, GuessTheCondition, Playground.

## 6. Open questions

1. Repository name and where the page lives (`LabConstrictor-Apps` on GitHub Pages, or a page on an existing site)?
2. Who maintains `verified.txt` (one person, or any lab member via PR)?
3. Should apps that have no tools (a pure notebook app) be listed? Proposed: yes, `hosts: [notebook]`.
4. Do we want a "last tested on" field per OS filled from the Playground's Check everything reports? Proposed: later, not in the first version.
5. Detection fallback for apps created before the file existed: also accept repositories whose `construct.yaml` and `.template_sync/manifest.yaml` match the template (listed as "unlabelled" until the file is added). Proposed: yes, but only in the catalog's log, not on the page.
