# Protocol reference (version 1)

## Schema (what hosts read)
`<registry>/<name>.schema.json`, generated by `labconstrictor-tools describe` without running any tool:

```
{ "protocol": 1, "application": str, "version": str, "tools_version"?: str, "features"?: [str],
  "tools": [ { "id", "label", "description"?,
               "inputs":  [ { "name", "label", "type", "required", "default"?, "description"?, "choices"?,
                              "minimum"?, "maximum"?, "unit"?, "axes"?, "pixel_size_of"?, "nullable"?, "group"?, "advanced"?, "enabled_when"?, "group_collapsed"?, "clear_after_run"?, "choices_from"?, "pick_channel"? } ],
               "outputs": [ { "name", "type", "axes"?, "display"?: {"apply_to", "relative_to"?}, "replace"? } ] } ] }
```
Value rules (enforced by the worker, each violation is a `FAILURE` with code `invalid_parameter` or a declaration error at registration):
* `boolean` must be a JSON `true`/`false` (never text or numbers); `choice` values must match a choice in type and value; a `float` is never a boolean.
* A parameter given as `null` is treated as not given: it takes its default, or (when `nullable`) the tool receives `None`. `Optional[...]` with a non-None default is refused when the app is registered (a host can only leave it at the default or unset).
* A default must be valid for its declared type (checked when the schema is generated, not when a host omits the value).
* A `choice` declared with an `Enum` annotation reaches the tool as the Enum member.
* An image/labels input with no pixels is refused (`empty_image`), from a file or from shared memory.
* Table inputs (a CSV file, UTF-8, first line is the header) reach the tool as a DataFrame exactly as written: floating point cells are read with every digit (`float_precision="round_trip"`, about twice as slow as pandas' default on very large tables); column names are kept as written, duplicates (`a,a`) and empty names included (pandas' renaming to `a.1` / `Unnamed: 0` is switched off, so a tool must address such columns by position); an empty cell is missing (NaN); the spellings `NaN`, `nan`, `NAN` mean a missing number (a column of numbers, `NaN` and empty cells, or of only `NaN` and empty cells, is a float column with NaN), and the other words pandas calls missing (`NA`, `N/A`, `NULL`, `None`, `null`, ...) stay text, except in a column whose other cells are all numbers, where they are missing numbers; a text column that happens to contain `nan` keeps it as text. A table file that does not exist is refused with `file_not_found`; one that is empty or not a UTF-8 CSV with `unreadable_table`; both messages name the file.
* `integer` and `float` values must be JSON numbers: text (even "3"), lists, objects, NaN and infinity give `invalid_parameter` (`'N' must be an integer, got text`, `'N' must be a number, got a list`, `'N' must be a finite number`); an integer-valued float such as `3.0` is accepted for an `integer`. A number beyond the float range is refused for a `float`.
* `file`, `folder` and `image`/`labels` values must be text paths: anything else gives `invalid_parameter` (`'N' must be a path (text), got a list: the host must send the file or folder path as text`).
* A shared-memory image descriptor must be `{"appose_type": "ndarray", "shm": {"name"}, "shape", "dtype"}` and the block must still exist and be large enough, with a numeric dtype; a stale or malformed one gives `unreadable_image` (`the shared-memory image for 'N' is gone or malformed (...): the host must keep the block alive until the task ends and send {...}`).
* What a tool returns must match its declaration, otherwise the task fails with `bad_return` and a message of the form `the <type> output '<name>' must be <what>, got <what arrived>` (an array of numbers for image/labels, a DataFrame / dict of lists / list of dicts for table and points, a dict for values, a path for file, text for message, a 3x3 matrix of numbers for affine). A tool with several outputs must return a tuple with one value per output (`tool returned N values, declared M`). An affine with NaN or infinity is refused (`bad_return`).
* Table and points outputs are written as UTF-8 CSV. A NUL character (`\\0`) in a column name or a text cell is refused with `bad_return` (`the table output 'X' has a NUL character in a cell of column 'c': remove it`), identically on every Python version; a lone surrogate or other character that is not UTF-8 is refused with `bad_return` (`... cannot be written as a UTF-8 CSV ...`). Line breaks, quotes and commas in cells and names are quoted and arrive unchanged.
* Image outputs: an empty array is `bad_return` (`image is empty (shape ...)`); complex, object, text and bytes arrays are `unsupported_dtype`; an integer image beyond 16 bits that float32 cannot hold exactly (more than 24 significant bits, for example a uint64 2**64-1) is refused with `unsupported_dtype` on every machine, never stored rounded or kept as 64-bit.
* Image outputs: integers are never changed in value (wide integers that fit 16 bits are stored as 16-bit; others must be exact as 32-bit float or the result fails with `unsupported_dtype`); floating point values are stored as float32 (about 7 significant digits); float values outside the float32 range fail.

Input `type`: `string integer float boolean choice image labels table file folder`.
`nullable: true` (additive, protocol 1): the parameter is optional AND has no default value (`= None` / `Optional[...]`). A host must let the
user leave it unset and then omit it from the request (the tool receives `None`); showing 0 or an empty string instead is a bug.
The notebook form does this with a "set" check box beside each nullable number, text, choice or yes/no (unchecked = greyed out and left out).
Number limits: the protocol, the command line and snippets carry integers of any size and floats up to the double range. A number box
never clamps silently. The notebook form has no made-up bound; because the page exchanges JSON numbers, an integer beyond +-(2**53 - 1)
(`notebook.MAX_FORM_INTEGER`) is refused with an `invalid_parameter` message, and the limit is in the control's tooltip. Declared `Min`/`Max` are enforced.
`group` (heading), `advanced: true` (listed under collapsed "Advanced settings") and `enabled_when: {"param", "equals"?}` (the parameter only applies when `param` is set/true, or equals one of the listed values) are presentation hints, additive within protocol 1: a host that ignores them shows the flat form, so a tool must accept every parameter whether or not it is "enabled". Group names are shown where they first appear.
Interaction hints (additive within protocol 1; a host that ignores them shows a plain form, so the tool must work either way):
* `group_collapsed: true` (with `group`): the group is an accordion section that starts folded.
* `clear_after_run: true`: after a successful run, hosts that keep form values between runs put the parameter back to its default (or unset). Fiji opens a fresh dialog each run and needs nothing.
* `choices_from: {"tool", "depends", "field"}` (string parameters): the options come from another tool of the app. The host runs `tool` with the current values of the parameters named in `depends` and reads the list under `field` of its `values` result; it shows a dropdown, and falls back to a text field when the call cannot be answered. The value stays a free string for the tool. Fiji builds its dialog before the user types anything, so it asks with the values used by the previous run of the same app (kept in `<LC_HOME>/state`) and falls back to the text field the first time.
* `pick_channel: true` (image inputs, `axes` YX or absent): the host lets the person choose a channel of the chosen image (names where the host has them, numbers otherwise) and sends the tool that channel only, as a 2D image. A host that cannot list channels sends the image as it is.
* output `replace: true` (image, labels, table, affine: the overlay): a new run replaces the previous result of the same output (same layer / window name) instead of adding "name [1]".
A GeoJSON dict returned for a `shapes` output is checked before anything is written: a `FeatureCollection` whose features are Polygon or MultiPolygon with non-empty coordinates (a Polygon is a list of rings, outer boundary first then holes; a MultiPolygon a non-empty list of polygons), every ring a list of at least 4 `[x, y]` positions (exactly two finite numbers), closed (last position equals the first) and with at least 3 distinct vertices, the same contract `_ring` gives to polygons built from `(y, x)` vertex lists. Anything else is `bad_return` naming the feature, polygon and ring. An empty result is a FeatureCollection with no features, never a feature with empty coordinates.

Output names are file names (`<name>.tif`, `.csv`, `.geojson` in the result folder), so `Name(...)` must be one portable file name: no `/`, `\`, `:`, `<>"|?*`, control characters or NUL, no `.`/`..`, no leading space or trailing space/dot, and not a Windows device name (`CON`, `NUL`, `COM1`, ...). Anything else is a `DeclarationError` when the tool is described; the writers also refuse (`bad_return`) a path that would leave the result folder.

`axes` (an input or an image/labels output) is a string of distinct labels from `T C Z Y X S`, one per array dimension, otherwise a `DeclarationError`. A declared output `axes` is a promise: an array with another number of dimensions is `bad_return` and nothing is written; without `axes` the host gets `YX`, `ZYX` or `CZYX` for 2, 3 or 4 dimensions and no `axes` claim otherwise.

`folder` is a directory path (the worker checks it exists); hosts show a folder chooser. Output `type`: `image labels table values affine file message points shapes`. `message`: `{text}` (plain text, short). `points`: `{path, n, columns, apply_to?}`, a CSV whose first two columns are `y` and `x` (finite pixel coordinates in the frame of the image named by `apply_to`, else of the first image); other columns are properties of each point. `shapes`: `{path, n, apply_to?}`, a GeoJSON FeatureCollection file (`.geojson`) of Polygon / MultiPolygon features, `[x, y]` coordinates in the same frame and with pixel centres at integers; feature properties are kept (a `label` property links an outline to its label). A host that does not know `shapes` lists the file.
Hosts must skip (and report) a schema whose `protocol` they do not support.

## Tools version and features
Additive within protocol 1 (an old host ignores both fields; a protocol change would be a new major version). Two fields say what produced a schema:
* `tools_version`: the `labconstrictor-tools` version that ran `describe` in the app's own interpreter (`labconstrictor_tools.__version__`, for example `0.2.0rc1`; tags are `v0.2.0-rc.1`, see [OPERATIONS.md](OPERATIONS.md#releases-and-tags)).
* `features`: sorted list of stable feature ids (`labconstrictor_tools.features.FEATURES`). An id means "this Tools implements that rule"; it is added in the change that implements it, never renamed, never reused.

Both are also written into the registry entry `<name>.json` by `register` (`tools_version`, `features`), read from the schema it just generated. **A missing field means unknown/old**: Tools before 0.2 wrote neither. `describe` prints them, and `doctor` shows them per app (`Tools 0.2.0rc1, features: ...`, or `Tools version unknown` for an old schema). The cached schema is not "stale" just because Tools was upgraded: `doctor` compares tools, not these two fields.

Feature ids (the implemented ones are in `FEATURES`; a planned id appears there with the change that implements it):

| Id | Meaning | Status |
|---|---|---|
| `reserved_inputs_v1` | the worker accepts and ignores reserved underscore inputs it does not know (`_job_dir`, `_calibration`, `_axes`, and any future `_name`) | in 0.2.0rc1 |
| `calibration_per_axis` | the worker copies the per-axis `_calibration` into the run record ([SPEC_WRONG_SCIENCE.md](SPEC_WRONG_SCIENCE.md) 2.3.4) | planned (registration/calibration PRs) |
| `retention_prune` | the CLI command `labconstrictor-tools prune [--root results\|runs\|all] [--dry-run] [--json]` and `labconstrictor_tools.retention`: only folders carrying a valid `.lc-owner.json` and a `.lc-done.json` are ever removed ([SPEC_WRONG_SCIENCE.md](SPEC_WRONG_SCIENCE.md) section 3; hosts only mark a run finished, then start `prune`) | in the first release after 0.2.0rc1 (not in 0.2.0rc1) |

### Compatibility rules for hosts
A host that needs a minimum states it as `(min_tools_version, required_features)` and applies the rules below to every schema it loads, with `labconstrictor_tools.compat.check_schema` (Python hosts: Napari, notebooks) or the same rules written in its own language (Fiji, QuPath; the data is in `conformance.json`, [CONFORMANCE.md](CONFORMANCE.md), `compat` section). The result is `ok`, `warn` or `refuse`, with one sentence for the person:
1. `protocol` not supported by the host: `refuse` (as today).
2. A required feature missing from `features` (or no `features` list at all): `refuse`, "needs <feature>; update the app's labconstrictor-tools".
3. `tools_version` missing (unknown/old) while a minimum is set: `refuse`; with no minimum set: `warn`, "Tools version unknown".
4. `tools_version` below the minimum: `refuse`. Below the optional `warn_below` version but not below the minimum: `warn`.
5. Otherwise `ok`. A `tools_version` the host cannot parse is `warn` (never a crash).
6. A host that starts `prune` after a run lists `retention_prune` in its required features, or checks the feature before it starts the subprocess: a Tools without it has no `prune` command. If the feature is missing the host starts nothing and never deletes a folder itself (SPEC_WRONG_SCIENCE 3.1.4); the folders then accumulate until Tools is updated.
Version order is PEP 440 for the forms used here: `0.2.0a1 < 0.2.0b1 < 0.2.0rc1 < 0.2.0 < 0.2.1`. A host in the release-candidate phase writes the minimum as `0.2.0rc1`.

## Result folders and run records (retention)
Under `<LC_HOME>` two folders hold what runs leave behind: `results/<YYYYMMDDTHHMMSS>_<6 hex>_<app>_<tool>` (the files of a run) and `runs/<time>_<app>_<tool>` (the run record). Feature `retention_prune`; the full policy is [SPEC_WRONG_SCIENCE.md](SPEC_WRONG_SCIENCE.md) section 3, in short:
* **Markers.** Whoever creates the folder (a host, the CLI, `runs.record`) writes `.lc-owner.json` first: `{"lc_marker": 1, "kind": "result|run", "name": "<folder name>", "host": "cli|napari|fiji|qupath|notebook", "pid": n, "created": "<UTC ISO-8601 with Z>", "token": "<uuid4>"}`, and `.lc-done.json` last, atomically (temporary file, then rename): `{"finished": "<UTC ISO-8601>", "status": "ok|failed|cancelled"}`. `labconstrictor_tools.retention.write_owner` / `write_done` are the reference writers.
* **Hosts never delete anything under `results/` or `runs/`.** After writing the done marker a host starts `labconstrictor-tools prune` in a subprocess and ignores its exit code; only Tools removes folders.
* **What `prune` removes**: the oldest folders beyond the newest 20 (`results`) or 50 (`runs`), counted over eligible folders only. Eligible = a real directory (not a symlink, junction or other reparse point) that is a direct child of the root, with a name of `A-Za-z0-9_.-`, a valid owner marker whose `name` is the folder's own name and whose `kind` matches the root, and a done marker. Foreign folders, legacy folders without a marker, folders with no done marker (active or crashed), links and files are never touched and never use up the quota. Order is the marker's `created`, then the name.
* **How**: one non-blocking lock on `<LC_HOME>/.retention.lock` (if it cannot be taken, `prune` exits 0 and deletes nothing); a folder is renamed to `.lc-deleting-<token>` inside the root, then removed without following links; a leftover of an interrupted removal is finished by the next `prune`. `--dry-run` lists exactly what a real run would remove and changes nothing. Exit code: 0, also when the lock is held; 1 when a folder that should go could not be removed (the report says which and why). `--out` folders, `state`, `logs` and everything outside the two roots are never touched.

## Reserved inputs
A request's `inputs` may carry fields that are not tool parameters. Their names start with an underscore and belong to the protocol; a tool cannot declare a parameter with one of these names (declaration error). **A worker accepts every name that starts with an underscore and ignores the ones it does not know**: a newer host may send a field an older worker predates, and that must never fail the task. Tools never see reserved inputs. The list (`labconstrictor_tools.protocol.RESERVED_INPUTS`, tested against this table):

| Name | Sent by | Meaning | Spec |
|---|---|---|---|
| `_job_dir` | every host | host-owned directory for outputs; the worker consumes it | this file |
| `_calibration` | hosts that send a `PixelSizeOf` value | per-axis pixel/voxel size with provenance (`x`, `y`, later `z`, `t`) | [SPEC_WRONG_SCIENCE.md](SPEC_WRONG_SCIENCE.md) 2.3.4 |
| `_axes` | hosts that write a file without axes metadata | `{param: "TZCYX"}`, the axes of the file just written | [SPEC_WAVE2.md](SPEC_WAVE2.md) |

Adding a name is additive within protocol 1: add it to `RESERVED_INPUTS` and to this table in the same change. **Order of work for issue #51 (reject undeclared inputs):** the worker must already tolerate the reserved names (this section) before #51 starts to refuse anything. #51 rejects exactly `convert.undeclared_inputs(schema, inputs)` (names that are neither declared nor reserved); it must not look at anything else. The worker refuses undeclared names with `invalid_parameter` (issue #51).

## Wire protocol (host <-> worker)
The worker (`python -m labconstrictor_tools serve --module M`) speaks the Appose worker protocol: one JSON object per line on stdin/stdout.

| Host sends | Worker answers |
|---|---|
| `{"task": id, "requestType": "EXECUTE", "script": "lc:<tool_id>", "inputs": {...}}` | `LAUNCH`, then `UPDATE {message, current, maximum}`*, then exactly one of `COMPLETION {outputs}`, `FAILURE {error, code, traceback?}`, `CANCELATION` |
| `{"task": id, "requestType": "CANCEL"}` | the task ends with `CANCELATION` if the tool calls `check_cancel()` |

Rules the worker enforces (each violation is written to the worker log/stderr):
* `task` must be a non-empty string and unique until the task's terminal response; an `EXECUTE` that reuses the id of a running task is ignored (answering would end the running task on the host).
* `script` must be text and `inputs` an object (or absent); otherwise the worker answers `FAILURE` with code `bad_request` instead of running the tool with defaults.
* A `CANCEL` for a task that is not running is ignored (it is not remembered for a later `EXECUTE`). Unknown `requestType`s, non-JSON lines and non-object lines are ignored. A request line longer than 16 MiB is dropped.
* A tool that calls `sys.exit()` or is interrupted ends with `FAILURE` (code `SystemExit`/`KeyboardInterrupt`); a result JSON cannot carry ends with `FAILURE` code `unserializable_result`.
* NaN and Infinity cannot be written in JSON: they are sent as `null`. A host must treat `null` in a numeric value as "not a finite number".


* `script` must be `lc:<id>` of a declared tool. **Anything else (e.g. Python source) is refused** (`unknown_tool`).
* `inputs`: image/labels/table/file values are file paths (an Appose `ndarray` shared-memory object is also accepted for images);
  scalars are JSON values; `_job_dir` (reserved) names the host-owned directory for outputs.
* `COMPLETION.outputs = {results: [...], job_dir, timings, diagnostics}`. A result is `{type, name, ...}`:
  `image/labels {path, axes}`, `table {path}`, `values {values}`, `affine {matrix_yx, apply_to, relative_to}`, `file {path}`.
* Closing stdin means "the host is gone": running tools are asked to cancel and the worker exits within 10 s. On every platform nothing a
  tool started outlives the worker: Windows puts them in a kill-on-close job object; on POSIX the worker makes itself the leader of its own
  process group at start (`setsid`, whoever started it, so no host has to) and sends SIGKILL to every other process of that group as its last act (found with `ps`; if that fails it kills the whole group, itself included).
* `UPDATE {message, current, maximum}`: `maximum` is 100 and `current` is the whole percent nearest to the fraction the tool reported
  (`progress(0.29)` -> 29); a tie goes up (0.295 -> 30), as Java's `Math.round` does. A host that shows or converts the fraction itself rounds
  the same way and never truncates.
* Shared-memory images: the host creates the block and unlinks it when it is done; the worker only maps and copies it and never unlinks it
  (it attaches without registering the block with its resource tracker).
* A request written to a worker that has already exited ends as `CRASHED` with the worker's last words (client side: `WorkerProcess.task`
  returns that task; it is not kept in `worker.tasks` and no exception reaches the host).
* Tools run on the worker's main thread; stdin is read on a helper thread (on Windows by polling, never a blocking read -
  native libraries touch the stdin handle during initialisation and a pending read would deadlock them).

## Registry
Entry `<name>.json` = `{name, display_name, version, prefix, python, module, pythonpath, runtime_path, schema_path, tools_version?, features?}` (the last two copy the schema's, see "Tools version and features"; an entry without them is from Tools before 0.2).
Search order (first wins): `$LC_HOME/apps` (default `~/.labconstrictor/apps`), the directories in `$LC_APPS_PATH`, then the system
directory (`%ProgramData%\LabConstrictor\apps`, `/Library/Application Support/LabConstrictor/apps`, `/etc/labconstrictor/apps`).
An entry is skipped and reported when its interpreter is missing, is not inside `prefix`, its file is not owned by the user / is
group- or world-writable (user directory, POSIX), or its schema is unreadable or has an unsupported protocol.
